## 一、项目结构

单体 Next.js 应用（前后端同项目，App Router），核心目录如下：

```
shantu-web/
├─ prisma/
│  ├─ schema.prisma           # 24 个数据模型（35KB）
│  ├─ seed.ts                 # 主初始化脚本
│  ├─ seed-admin.js           # 管理员初始化
│  ├─ seed-members.js         # 会员初始化
│  └─ seed-wechat.ts/.js      # 微信配置初始化
├─ src/
│  ├─ app/
│  │  ├─ (site)/              # 官网：首页/服务/案例/博客/关于/联系/定价/会员中心
│  │  ├─ admin/               # 后台：登录 + 24 个管理页面
│  │  ├─ api/                 # 130+ 个 Route Handler
│  │  ├─ login/ pay/ member/  # 独立页面
│  │  ├─ sitemap.ts robots.ts # SEO
│  │  └─ middleware.ts        # /admin 访问控制
│  ├─ components/             # 前台组件 + admin/ 后台组件（约 50 个）
│  └─ lib/                    # 认证/支付/合同/实名/AI/限流/工具（约 30 个）
├─ uploads/ assets/ public/   # 上传文件、字体证书、静态资源
├─ deploy.sh                  # 部署脚本
└─ dist/                      # 构建产物（distDir 自定义为 dist）
```

**结构问题**：
1. 根目录残留大量历史产物：5 个 `dist_bak_*`/`dist.bak-*`/`dist_broken_*` 构建备份目录（约 1.5GB）、`.src-backup-*` 源码备份、`.env.bak-*`、`_build.log`、`_assess.sh` 等临时脚本。
2. `src/lib` 下残留大量 `.bak-*` 文件（ai.ts、contract-pdf.ts、realname.ts 等均有多份历史备份）。
3. 无 `docs/` 目录、无 `tests/` 目录、无 CI/CD 配置。

## 四、缺失功能（对比 2.0 规划）

1. **小程序前端代码**：项目内只有 miniapp API，**无 `.wxml/.wxss/.js` 小程序前端**（原小程序前端位于已删除的 `tujing_v2/miniprogram`、`tujing-platform/miniapp`，本次审计确认已丢失且无备份）。
2. **服务周期（ServicePeriod）独立模型**：项目只有 startAt/endAt，无独立服务周期表，无法支撑"一个项目多个服务周期/续费"。
3. **任务（Task）模型**：无任务/负责人/截止日期模型，日报直接挂在 Project 下。
4. **通知（Notification）模型**：无站内信/消息推送。
5. **订单明细（OrderItem）**：订单是单一套餐（packageId），不支持多商品组合订单。
6. **完整状态机**：合同仅 3 状态、任务/日报/服务周期状态机未建模。
7. **退款/续费完整流程**：有退款字段但续费流程未实现。
8. **客户中心（小程序「我的」升级版）**：服务进度、月报查看等部分 API 已备，前端缺失。

## 七、API 问题

1. **API 数量庞大（130+），但无统一响应契约**：`lib/api.ts` 有 `ok/fail/handle` 助手，但部分接口返回结构不统一，错误码（`code`）未全局枚举化（提示词要求 `{success, code, message}` 统一结构）。
2. 状态码使用不统一：部分 401/403/409 由业务层 `fail()` 显式传，部分走默认。
3. 无 API 版本化（`/api/v1`），未来小程序/后台接口演进会互相影响。
4. 无 OpenAPI/Swagger 文档，接口靠代码自读。
5. 小程序管理后台 API（`/api/miniapp/admin/*`）与电脑后台 API（`/api/admin/*`）存在功能重复（订单、线索、项目各一套）。

---

## 八、数据库问题

1. **无 migrations 目录**：用 `prisma db push` 直推，无 migration 历史，无法安全回滚/追踪结构变更（P1）。
2. **状态字段类型混用**：`OrderStatus/LeadStatus/ProjectStatus/AdminRole` 用 enum，但 `Service.status/Case.status/Article.status/Order.type/Payment.status/Contract.status/RealNameAuth.status/Coupon.discountType` 等用 String，存在非法状态写入风险。
3. **字段命名不一致**：多数字段用 `@map` snake_case，但 `Project.name/manager/note`、`Package.period/price`、`AiProvider.provider/name/model` 等直接用 camelCase，与整体风格不一致。
4. **关系外键策略不一致**：Contract.orderId 是 `@unique`（一单一合同），但 Project.orderId 无 unique（一单可多项目？语义不清晰）。
5. **AiChatMessage 关系缺 onDelete**：member/project 关联无 onDelete 指定，删除会员/项目可能因外键约束失败。
6. **金额字段类型不统一**：`Order.amount/Package.price` 用 Int，`ProjectDailyLog.gmv/views` 用 BigInt。
7. 软删除字段（deletedAt/deletedBy/deleteReason）在 7 个模型重复，未抽公共基类（Prisma 不支持继承，但可约定）。

## 九、支付问题

**做得好的（安全基线）**：
- 订单创建**后端查价**，前端不传金额（`finalAmount = pkg.price - discount`）。
- 支付金额以服务端订单为准（`amount: order.amount`）。
- 微信回调**平台证书验签 + AES-256-GCM 解密**，验签失败忽略回调。
- `confirmPaid` 事务内**金额一致性校验 + 幂等**（PAID 返回 duplicated）。
- Mock 支付 **fail-closed**（生产禁用 + 需显式 `ENABLE_MOCK_PAYMENT=true`）。
- 支付前置**合同已签署校验**（后端硬校验）。
- 下单限流（同 IP 60 秒 5 次）。

**风险点**：
1. Mock 支付在生产可通过 `PAYMENT_PROVIDER=MOCK` 环境变量启用（当前 `.env` 为 `PAYMENT_PROVIDER="WECHAT"`，安全；但需确认生产不会误改回 MOCK）。
2. 限流为**内存 Map**，单实例 PM2 fork 模式可用，多实例/重启失效。
3. 退款无自动对账/定时补偿，依赖手动触发。
4. 易支付（第三方）回调验签逻辑未在本次审计逐行核对（见 YipayProvider，需专项复核）。
5. 微信 H5 支付降级 Native 扫码逻辑：`catch` 后静默降级，可能掩盖真实报错。

## 十、合同问题

1. **合同状态机仅 3 态**：`PENDING / SIGNED / VOID`，缺少 2.0 规划要求的 `DRAFT / PENDING_REAL_NAME / PENDING_CONFIRM / PENDING_SIGN / ACTIVE / CANCELLED / EXPIRED`。
2. 合同与实名认证的时序约束不明确（"先实名再签"还是"先签再实名"未在模型层强约束）。
3. 签名信息（signatureImageUrl/signedAt/signIp/signUserAgent/signOpenid/signNickname）直接堆在 Contract 表，无独立签名记录模型（无法支持多次签署/骑缝章等）。
4. 合同版本日志（ContractVersion）记录了字段 diff，是亮点；但缺「合同作废原因」结构化字段。
5. 合同 PDF 生成依赖 pdfkit 字体路径硬编码（`assets/fonts/NotoSansSC-Regular.otf`），字体文件需确认存在于生产。

---

## 十一、认证问题

**做得好的**：
- 管理员/会员会话分离（不同密钥派生）。
- JWT 密钥 fail-fast（无弱密钥回退）。
- 数据加密密钥（APP_ENC_KEY）与会话密钥（AUTH_SECRET）职责分离。
- 密码 bcrypt（cost 10）。
- 管理员登录日志（成功/失败都记）。

**风险点**：
1. JWT **无 refresh token**，7 天固定过期，无主动吊销（管理员改密/禁用后旧 token 仍有效 7 天，虽有 `isActive` 二次校验，但只针对 admin）。
2. 会员 token 无吊销机制（拉黑 status=BLOCKED 后，旧 token 仍可通过 `verifyMemberToken`，仅 `getActiveMember` 二次查库拦截；需确认所有会员接口都走了 `getActiveMember`）。
3. 微信登录（`wx.login` → code2session）链路需专项核对 secret 是否只在服务端使用。
4. 无登录限流（管理员登录失败是否限流需确认，README 提到"防爆破告警"但实现需核对）。

## 十二、权限问题

1. RBAC 已实现（5 角色 + PermissionKey 白名单），SUPER_ONLY 模块（wechat/payment/admins/settings/recycle/logs）仅超管可见——**做得较好**。
2. 小程序管理端复用 `admins.open_id` 白名单 + 角色写权限（canMiniWrite），逻辑清晰。
3. **越权防护核心点**：支付/合同/项目/日报等接口是否逐条校验 `memberId === 当前会员 id`，需在阶段四逐接口复核（审计已确认支付接口有此校验）。
4. 财务/只读角色的「查看」与「编辑」边界，依赖前端隐藏 + API 校验双层，需确认 API 层完整覆盖。

## 十三、安全问题

**已确认的安全防护（亮点）**：
- 支付金额后端校验 + 幂等 + 验签 ✅
- Mock 支付 fail-closed ✅
- 敏感密钥 AES-256-GCM 加密落库（微信 AppSecret/APIv3 密钥/商户私钥/身份证）✅
- JWT 密钥 fail-fast，无弱密钥回退 ✅
- 后台/接口 `X-Robots-Tag: noindex`，robots 禁 `/admin` `/api` ✅
- 表单限流、Zod 校验、上传类型/大小限制、路径穿越防护（README 声明）✅

**风险点（P0/P1）**：
1. **默认管理员账号 `admin / Shantu@2026`** 明文记录在 README 与 seed 脚本（P0，上线必须改）。
2. **MySQL root 密码为弱密码 `admin`**（宝塔记录一致，P0）。
3. **无 Git 版本控制**：项目不是 git 仓库，无版本历史、无远程备份、无法审计变更（P1）。
4. 生产密钥（AUTH_SECRET/APP_ENC_KEY）依赖 `.env`，`.env.bak-*` 残留多份历史版本（含旧密钥），建议清理。
5. 敏感信息扫描需在阶段二完整执行（`.env`、`*.pem`、`*.key`、`*.p12`、Git 历史）。

## 十四、性能问题

1. 服务器仅 2C/1.7G 内存，Next.js 构建时需 `--max-old-space-size=1024` 限制，构建已踩过 OOM。
2. 官网图片需确认是否统一 WebP + 懒加载（媒体库上传已压缩 WebP ✅，但案例/文章封面需核对）。
3. 数据库 N+1 风险：案例/文章列表关联查询需确认是否用 `include` 导致 N+1。
4. 无缓存层（Redis），套餐/案例/文章/服务全走数据库实时查询，高并发下压力大（当前规模可接受）。
5. `visit_logs` 每次访问写库，长期数据量增长需归档策略。
